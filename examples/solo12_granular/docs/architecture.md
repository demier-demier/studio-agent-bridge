# Architecture, decisions and threat boundaries

## Simulation loop

1. Seed and settle a shallow sphere bed for 0.28 simulated seconds.
2. Initialize Solo12 as a free rigid body with twelve joint motors.
3. Compute joint commands with a scheduled crawl and feedback controller.
4. Read the current foot centers, linear velocity and angular velocity from MuJoCo.
5. Advance the particle solver through twenty 50 μs substeps per 1 ms rigid step for the video preset.
6. Average particle reaction forces and torques across those substeps and apply them to the foot bodies.
7. Advance MuJoCo and recompute the just-integrated transforms.
8. Stream particle positions, mesh transforms, foot centers, joint states and measured loads to disk at approximately 30 Hz.

The foot torque uses the center-to-contact arm. Angular foot velocity contributes to the contact-point velocity. Analytic checks cover these signs and action–reaction pairs. The particle spatial grid clears previously occupied cells instead of scanning the full dense grid, while overflow and out-of-bounds conditions are detected.

The body's motion is an integration result. There is no body-position animation, external support actuator or generated motion model. Classical feedback is applied through joint torques. The rigid substrate supplies most vertical support in this specific shallow-layer case; that contribution is retained and reported.

## Rendering and editing

The renderer reconstructs official Solo12 meshes from the numeric geometry package and instantiates grains at recorded positions. It varies the camera, lighting and materials. Rendering and physics are separate stages, allowing each to use the Metal GPU without running two GPU-heavy jobs concurrently.

The 16-second edit contains 7.2 seconds of continuous recorded walking, a 3-second replay from the contact camera, a 2.8-second final-state track view and a 3-second closing card. Source motion plays at its recorded rate. The track view is a still with a small crop animation, not additional simulated time. Recorded foley is synchronized to detected primary scheduled footfalls; music and sound design are presentation assets.

## Important decisions

- **Use an open robot:** upstream Solo12 meshes and inertial data are pinned to a public commit. Four experimental spherical pads and a feedback crawl are explicitly documented changes.
- **Stream the cache:** the million-particle trajectory is memory-mapped to avoid retaining multiple full trajectories in unified memory.
- **Keep backend choice explicit:** CPU permits a bounded installation/integration check; Metal is used for the recorded full run. A silent fallback could make an unexpectedly slow run look like an accelerated one.
- **Preserve failures and limits:** rejected visual drafts are not presented as final outputs. Source evidence distinguishes the historical full run from tests of the portable release package.
- **Keep the physics claim narrow:** no learned policy, hardware validation, deep-sand calibration, real-time claim or competitor parity claim.

## Threat and resource model

This example is a local CLI workflow, not a hosted multi-user service or sandbox. It does not accept prompts, connect to model APIs or execute commands generated by an LLM. Python, Blender and FFmpeg run with the invoking user's filesystem permissions.

Use trusted source code and dependencies in a dedicated environment. Large particle counts, tiny timesteps, long trajectories and high render resolutions can exhaust memory or disk; use the smoke preset before increasing workload. Keep generated runs outside source control. A run that fails a guard is incomplete evidence, not a valid simulation result.

Do not load arbitrary untrusted simulation caches or robot descriptions into a privileged environment. Numeric cache readers use NumPy without pickle loading. Blender scripts create a fresh scene instead of opening arbitrary supplied `.blend` files. These boundaries reduce accidental execution paths; they do not make third-party native software or malformed files safe.

The published evidence contains no local account paths, credentials, private social screenshots or operational logs. Public source attribution is retained separately from the author's private production workspace.
